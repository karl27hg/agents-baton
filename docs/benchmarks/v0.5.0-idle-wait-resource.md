# Baton v0.5.0 Idle Wait Resource Check

This document records an indicative local resource check for Baton's automatic polling behavior. It is benchmark evidence, not a runtime requirement or a general hardware guarantee.

## Scope

The check answers two operational questions:

1. Does an idle Baton waiter busy-spin or consume enough CPU to be a likely source of hardware heat?
2. How do CPU, memory, SQLite state, and lease cleanup change when multiple waiters share one database?

The check covers idle `wait` processes only. It does not measure the separate workload of Codex agents running builds, tests, browsers, containers, or other tools.

No direct temperature sensor data was collected. CPU time, process state, resident memory, and database growth were used as operational indicators. Thermal behavior still depends on the machine, ambient conditions, power mode, and unrelated workloads.

## Method

Each scenario used a temporary database outside the Baton repository.

Single-waiter timing used `/usr/bin/time -p` around a 9-second empty-queue wait. The multi-waiter check started ten independent Python processes against one database, sampled their process state and RSS, and summed `/usr/bin/time -p` output over a 15-second timeout.

The checks also inspected:

- active and remaining rows in `waiter_leases`
- Baton database size before and after idle waiting
- remaining SQLite WAL or journal files
- process exit status after timeout

Exit status `2` was expected because the queues remained empty until timeout.

## Interpretation

- The measured waiters slept between checks and did not exhibit busy-spin behavior.
- The measured CPU load is unlikely to be a meaningful heat source by itself on the tested machine.
- Memory scales more directly than CPU because every waiter is a separate Python process. Ten waiters used about 232 MiB RSS; a much larger worker pool can create memory pressure and indirect swap activity.
- Numeric fixed intervals, especially `--interval 1`, bypass automatic sleep scaling for those processes and can raise aggregate CPU and SQLite activity.
- Real agent work such as compilation, browser automation, test suites, containers, and local media processing is more likely to cause heat than Baton's idle wait loop.
- Automatic polling bounds the target interval at 30 seconds. With ten or more active waiters, each automatic waiter targets that cap with stable jitter, reducing synchronized SQLite access.

For normal local use with a small number of role agents, no Baton-specific thermal mitigation is indicated by this check. For dozens of persistent waiters, measure the target machine and consider a future single-daemon notification model to reduce per-process memory overhead.

## Reproduction Notes

Start with an empty temporary database and verify the installed version:

```bash
DB="$(mktemp -d /tmp/baton-resource.XXXXXX)/baton.sqlite3"
bin/baton --version
bin/baton --db "$DB" init
/usr/bin/time -p bin/baton --db "$DB" wait --role frontend --timeout 15
```

For a multi-process check, start the intended number of waits against the same temporary database, inspect them while active, then confirm every process exits and `waiter_leases` returns to zero. Do not run resource experiments against a live project queue.

## Distribution Policy

Keep benchmark evidence in the source repository under `docs/benchmarks/` so maintainers can review how operational claims were derived. It does not need to be uploaded as a separate GitHub Release asset.

- Source clones, submodules, and GitHub source archives include this document naturally.
- Release notes should link to it when polling or resource behavior materially changes.
- Minimal runtime-only packages may omit benchmark documents because Baton does not read them at runtime.
- README should retain only the stable operational guidance and a link to the evidence.
